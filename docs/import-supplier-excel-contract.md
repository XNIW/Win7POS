# Supplier Excel Import Contract

Android is the canonical source for supplier Excel import behavior. The current comparison baseline is Android main `4b2b4a93dd5d4db7d1cfb83e897aa5cbac40366e`; the cross-platform classification and intentional exclusions are recorded in `docs/reports/2026-08-03-current-android-import-parity.md`. Public import keys are: `barcode`, `productName`, `itemNumber`, `purchasePrice`, `retailPrice`, `quantity`, `supplier`, `category`, `secondProductName`, `totalPrice`, `rowNumber`, `discount`, `discountedPrice`, `oldPurchasePrice`, `oldRetailPrice`, `realQuantity`, `complete`.

Forbidden names such as `stockQuantity`, `supplierName`, `categoryName`, `articleCode`, `unitPrice`, `name`, `name2`, `cost`, `prevPurchase`, and `prevRetail` are allowed only as storage/model boundary details or legacy aliases normalized before preview.

UX workflow: supplier import is a four-step wizard: file selection, column analysis/mapping, editable row correction, then DB sync preview/apply. The editable row step must allow editing `purchasePrice`, `retailPrice`, `quantity`, `supplier`, and `category` before apply. The bulk helper can calculate `retailPrice` from `purchasePrice` using a markup percent, rounding to 10/50/100 CLP, and an apply-only-empty option. `purchasePrice` must never silently auto-fill `retailPrice`; new products without `retailPrice` are blocked until the user fills the value or uses the helper.

Detection policy: normalize headers by trim/lowercase/diacritic removal/space and underscore removal/non-alphanumeric removal. Match the normalized whole header and exact fragments split on slash, backslash, colon, parentheses, brackets, braces, pipe, semicolon, newline, whitespace, and CJK/Latin script runs. Fragment matching is exact; substring matching is forbidden. Row profiles use `nonBlankCount >= 4 && numericCount >= 2 && textCount >= 1`. A clean one-row header with at least three canonical aliases retains the legacy fast path. Otherwise detection finds the first repeated data-like row and examines at most the two immediately preceding non-data-like rows; two rows are merged column-by-column only when the combined alias evidence improves on the immediate row. Metadata before those header rows remains excluded and original source row numbers remain stable. Headerless input uses generated columns. Each column keeps `headerSource` as `alias`, `pattern`, `generated`, or `unknown`; required `barcode`, `productName`, and `purchasePrice` are generated when missing.

Pattern policy: analyze at most 40 rows and require at least two samples when more than one data row exists. Barcode, item number, product name, quantity, and purchase price candidates use the current Android weighted column profiles. Quantity scoring penalizes a `1..N` sequential row-number shape. Purchase/total pairing requires `totalPrice` to match `quantity * purchasePrice` within 10% for at least 70% of informative samples. A pattern candidate needs score `>= 0.45` and must beat the runner-up by more than `0.08`; otherwise it remains unassigned for manual Step 2 mapping. Confidence is `low`, `medium`, or `high`. The retained Win7 compatibility tie-breaks require additional catalog structure (product name adjacent to barcode, quantity adjacent to product name, or a strict alphanumeric item shape); they have explicit reason codes and never resolve an ambiguous barcode or price candidate. Headerless files retain the established supplemental inference for retailPrice, secondProductName, supplier, discount, discountedPrice, and rowNumber.

Detection diagnostics are bounded to the public field list, at most three candidates per field, at most four canonical reason codes per candidate, two header-row indices, and 40 sampled rows. Diagnostics contain field, selected column, confidence, decision reason, candidate column, score, and reason codes only. Worksheet cell values are never copied into the trace. The WPF workflow writes this bounded structural trace to diagnostics without adding import data to the operator UI.

Receiving workflow scope: `realQuantity` precedence over `quantity` is retained because it was already part of the shared canonical import behavior. Android-only discount application, old-price override semantics, complete state, payment totals, receiving history/export, and mobile lifecycle behavior are not added to the Win7POS catalog apply path by this parity change.

Rows: filter summary rows with the exact Android token set `合计`, `总计`, `小计`, `汇总`, `合計`, `總計`, `小計`, `總結`, `总额`, `subtotal`, `total`, `totale`, `tot.`, `sommario`, `resumen`, `sum`; parse `1.234,56`, `1,234.56`, `1234,56`, and `1234`; duplicate barcodes keep the last occurrence, warn with row numbers, and do not sum quantity.

Boundary mapping:
- Android: `quantity -> stockQuantity` and other canonical keys map to Room `Product` fields only inside analyzer/repository apply.
- iOS: `quantity -> stockQuantity` and other canonical keys map to `ProductDraft`/SwiftData fields only inside `ProductImportCore`.
- Admin: canonical preview/import rows map to API/database schema only inside server apply/merge functions.
- Win7POS: `itemNumber -> ImportRow.ArticleCode / product_meta.article_code`; `productName -> ImportRow.Name / products.name`; `secondProductName -> ImportRow.Name2 / product_meta.name2`; `retailPrice -> ImportRow.UnitPrice / products.unitPrice`; `purchasePrice -> ImportRow.Cost / product_meta.purchase_price`; `quantity -> ImportRow.Stock / product_meta.stock_qty`; `supplier -> SupplierName` only inside the adapter; `category -> CategoryName` only inside the adapter.

Catalog import Admin Web sync contract:
- Boundary is always `Win7POS -> Admin Web/Admin Console API -> Supabase`. Win7POS must not call Supabase directly and must not store service-role credentials.
- Local schema version is `pos-catalog-import-v1` (`PosOnlineContract.CatalogImportSchemaVersion`).
- Local durability starts in `catalog_import_outbox`; supplier Excel apply enqueues a `pending` import in the same SQLite transaction as the product/meta/price-history mutations. Dry-run, no-change, and failed imports do not enqueue.
- Outbox payload is normalized canonical data only: `clientImportId`, `idempotencyKey`, `schemaVersion`, `source`, `payloadHash`, operator/shop/device context, and items keyed by barcode plus canonical fields. Do not store the original Excel file bytes in the outbox.
- Status values are `pending`, `retry`, `acked`, and `failed_blocked`; retry uses `attempt_count`, `next_retry_at`, `last_attempt_at`, `last_error_code`, and `last_error_at`.
- Server ack must return an Admin Web import id and canonical remote product/price identifiers or a blocked conflict reason. The client then follows with catalog pull to converge on Admin's canonical state.
- HTTP sync is intentionally not implemented until Admin Web publishes the endpoint, auth scope, conflict policy, and response schema. The expected endpoint is `POST /api/pos/catalog/import-sync`, but Win7POS must not add a live client call until that contract exists server-side. Expected ack statuses are `accepted`, `duplicate`, `idempotent`, `validation_failed`, and `conflict`; accepted/duplicate/idempotent map to `acked`, retryable transport/server failures map to `retry`, and validation/conflict failures map to `failed_blocked`.

Supplier Apply revalidation and transaction contract:
- The established Step 4 preview fingerprint remains byte-for-byte stable and is still rebuilt and compared before backup. Separate apply expectations record existence, product identity, active/meta state, product/meta decision fields, supplier/category identities, and original source row for every effective last-wins barcode. A second expectation records the normalized official shop id/code and `pos.catalog.transition_epoch`; neither expectation changes the cross-platform fingerprint.
- Step 4 loads its targeted products and shop/account expectation from one read transaction while holding `CatalogShopTransitionBarrier`. Apply holds the same barrier, opens one explicit SQLite transaction, loads only the effective barcodes in deterministic parameterized batches of 500 plus one bounded shop-context query, rebuilds Step 4 against that transactional snapshot, and compares the unchanged preview fingerprint and both expectations before any supplier, category, product, meta, history, or outbox write.
- The pinned `SQLitePCLRaw.bundle_e_sqlite3` provider reports `MAX_VARIABLE_NUMBER=32766`; 500 is intentionally conservative for bounded SQL text and Win7/x86 allocations. No full catalog is materialized and the normal Apply path has no per-row existing-product query fallback.
- Product staleness is state-equivalent and target-scoped, not a global catalog-revision fence: changes to an affected barcode are rejected; unrelated product changes do not invalidate the preview; a same-row change restored to the exact expected state remains valid. A real shop transition always invalidates the preview even when the target barcode remains absent. Missing context, changed shop, changed transition epoch, missing, newly inserted, hard-deleted, soft-deleted, replaced, meta-changed, and decision-field-changed states have deterministic `SUPPLIER_IMPORT_STALE_PREVIEW` reasons.
- Cancellation is accepted before and during batch preload/revalidation and is checked throughout reference and product/history writes. Any cancellation after the transaction starts rolls the transaction back completely and propagates cancellation; the shipping wizard retains its existing UX of exposing Cancel only for analysis, so it does not introduce a new mid-Apply UI action.
- Supplier/category names are batch-read with the existing trim/case/newline semantics, each genuinely missing normalized name is inserted once, and prepared insert commands are reused. Prepared product/product_meta commands are reused per change. Purchase and retail history for one source row may share one prepared two-value insert command, while retaining two distinct audit rows with exact old/new values, original barcode/client item identity, and `IMPORT` source.
- Catalog import outbox enqueue remains inside the same transaction after all writes and revalidation. Dry-run, no-change, stale, cancelled, or failed Apply creates no outbox row. Test-only internal fault hooks cover post-preload, post-revalidation, post-reference-resolution, product/history write counts, and both sides of outbox enqueue; they are not exposed through production UI or configuration.

Excel readers must support real `.xlsx`, real `.xls`, and simple HTML table exports saved as `.xls` when the platform reader supports those formats. Win7POS handles HTML `.xls` with an internal table parser so no new Win7-incompatible UI/runtime dependency is introduced.

Reader materialization and x86 bounds:
- ExcelDataReader is the normal row-by-row reader for real `.xlsx` and binary `.xls`; the first result is read completely and disposed before a raw table is returned. `AsDataSet` is not allowed in the supplier first-sheet or sheet-count paths.
- ClosedXML is a compatibility fallback for `.xlsx` files ExcelDataReader cannot open and for a first worksheet containing formulas, because current ClosedXML formula behavior is part of the supplier preview contract. Formula probing reads only the first worksheet XML and does not retain it.
- Worksheet count advances ExcelDataReader results with `NextResult()` and must not create worksheet row lists or DataSet tables. Import always selects the first worksheet, even when later worksheets are larger.
- Reader rows are normalized once and their owned buffers transfer into raw-table rows. No lazy row iterator may outlive the workbook stream.
- Limits are centralized in `SupplierExcelImportLimits`: 32 MiB input file, 60,000 worksheet rows, 256 columns, 1,000,000 logical cells, 32,767 characters per cell, 16,000,000 aggregate retained characters, 4 MiB per OOXML metadata part, 256 MiB streamed first-sheet XML, and 4,096 candidate HTML tables. Every parser reads through a handle whose visible length is fixed at open time, so concurrent growth cannot bypass the input bound. The 50,000-row x 12-column fixture is accepted. Stable diagnostic codes are localized only at the WPF boundary.
- Analyze cancellation is cooperative at no more than 64-row intervals through reading, raw-table construction, preliminary analysis, and final analysis. Busy Cancel requests cancellation instead of closing the wizard; cancellation returns no partial raw table or analysis, releases the file, performs no supplier apply, and leaves Step 1 reusable.

Win7POS operator workflow:
1. Open Products/Catalog or Database/Maintenance and choose `Import Excel fornitore`.
2. Choose the supplier `.xls`/`.xlsx` file.
3. Review Step 1 sheet/header/row counts and warning/error summary.
4. In Step 2 set any wrong column to the Android canonical key, or disable columns that should not import.
5. Click analyze/continue so Step 3 rebuilds from the corrected mapping.
6. In Step 3 edit `retailPrice`, `purchasePrice`, `quantity`, `supplier`, or `category`; for new products with empty `retailPrice`, use the bulk helper or type the values.
7. Continue to Step 4 and review the DB sync preview: new products, updates, no-change rows, skipped rows, warnings, and blockers.
8. Apply only after the button is enabled; the summary shows backup path, inserted, updated, skipped, warning count, and error count.

Operational state policy:
- `ready_to_apply`: Step 3 preview has required values; the user reviews and applies.
- `ready_after_mapping_override`: Step 2 needs a canonical mapping correction, then the same file can continue.
- `ready_after_price_edit`: Step 3 needs retail price entry or the bulk helper, then the same file can continue.
- `business_blocked_missing_barcode`: the workbook row must be corrected or removed before apply.
- `unsupported_or_corrupt_with_clear_message`: the app shows a recoverable file-format message.

Admin web import is intended for normal/smaller workbooks. Win7POS offline import is the recommended path for large or complex supplier files and for store-side offline operation; Admin must show a clear message routing over-limit files to Win7POS or split workbooks.
